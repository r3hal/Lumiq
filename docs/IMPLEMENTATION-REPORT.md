# Feature audit implementation report — Focal 1.4, build 5

## Existing behavior preserved

SwiftUI/ObservableObject architecture, native AVFoundation preview and full-quality photo capture, manual zoom/focus/flash, original screenshot-based camera layout, grid/level, Vision detection/tracking and auto framing, supported RAW/ProRAW, private protected-file library, favorites, sharing, Photos export, scans/captions, Settings and the field guide. These are real source implementations. This workspace has not independently run them on an iPhone.

## Existing fixes/completions

- Failed/partial session setup cleans up before retry. Camera switching has rollback and disables capture during reconfiguration.
- Capture timeout plus capture-ID checks avoid a permanently busy shutter and reject late results from an earlier operation.
- Front mirroring is centralized in PreviewProjection for points and boxes; native preview and processed photo connections are mirrored consistently while analysis stays unmirrored.
- Camera checking/retry UX; Photos export denial Settings recovery; a missing/invalid motion reading no longer displays a green level or produces readiness.
- Cancelled thumbnail loads cannot overwrite a newly selected variant. Source metadata uses selected-file dimensions.
- Odd-size crops stay inside the image; aspect derivatives preserve supported metadata, reset orientation/dimensions and retain the original file.
- Stale reference scan/readiness/coach measurements clear on reset. Paired-file deletion attempts every file; storage counts actual container files.
- Field guide uses its host navigation stack and has a working Done action instead of creating a nested hidden navigation stack.

## Dependencies and setup

No third-party packages, model downloads, paid services, backend or client secrets added. New native imports: PhotosUI/system photo picker, CoreLocation (optional user-triggered permission), ImageIO/UniformTypeIdentifiers for image encoding and metadata. Core Image was already used. iOS remains 17+; supported shutter suppression requires iOS 18+.

`NSLocationWhenInUseUsageDescription` is generated by the existing project script. PhotosPicker does not request broad library-read access; existing Photos export requests add-only access. Location is not stored, uploaded or embedded in photos. Solar calculations follow the [NOAA equations](https://gml.noaa.gov/grad/solcalc/solareqns.PDF); they use a defined −4° to +6° interval and one-minute sampling, with no weather/terrain/refraction correction.

## Validation

Automated checks run here: Swift grammar parsing, PBX project/resource and source-reference validation, plist/scheme XML, asset/font files, Python generator compilation/determinism, YAML and shell syntax, test registration/count, diff whitespace. These are structural checks, not a Swift type check or native build.

## Remaining partial/missing items and blockers

- Generative photography/pose coaching, semantic clutter understanding and AI aesthetic quality judgment: native detections and honest measured heuristics are present; a suitable model/service is not. A future hosted model would require a backend/credentials and server-held secrets; no key should be embedded in iOS. Specific proprietary Framed descriptions are not guaranteed.
- Camera live-filter rendering: the editor previews real effects, but the camera intentionally retains its native unfiltered preview. Matching real-time camera effects requires a separate validated Core Image/Metal display pipeline and hardware performance/color checks. No fake live-filter button exists.
- Native high-speed burst and Apple-style Night mode: sequential full-quality series and low-light tips/available device boost are present; these are not the specialized pipelines.
- RAW/silent shutter/lens capabilities are device dependent. Reference images are session-only. Collections currently assign a photo to one named group. Edited JPEGs use sRGB; original/RAW data stay intact. Full-screen display decodes a bounded 6000-pixel preview; sharing/export uses the source file.
- Physical/native validation remains the main blocker to labeling these hardware features “implemented and working.” All new feature UI routes have real actions; no disabled placeholder purchase/model feature is added.
